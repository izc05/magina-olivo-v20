# Response to independent review of ea3c25f

## P1-A — current owner recovering its own live request

Confirmed before editing with production DAO SQL: claim=1, mark=1, recovery with the
same owner's marker=1. Namespace-only markers did not establish a new acquisition.

Each lease now has one random UUID epoch generated at acquisition. A V2 marker contains
the canonical namespace hash and this epoch. It stays stable while that lease is held;
another acquisition in the same namespace must have a different epoch. Recovery validates
the canonical marker structure, the same namespace and a DIFFERENT owner epoch. The DAO
also rejects equality and compares the previous stored marker atomically. Old V1 and
unmarked claims remain blocked; no unverifiable owner is inferred.

The SQL regression explicitly tries recovery with the current owner and then reclamation:
both return 0 and PROCESSING/attemptCount remain unchanged. The existing Room handoff
test now makes this same-lease call before releasing ownership and requires false.

## P1-B — actual edits lost account attribution

Confirmed by reading DeliveryWriter: both create and rewrite omitted accountId. The
manual SQL attribution in the previous fixture made that test narrower than the product
flow; it is removed from the recovery fixture.

Production AppCompositionRoot now injects LocalFarmLinkRepository as DeliveryWriteScope
into the manual Delivery repository. It holds the AccountRepository mutex while reading
the durable farm consent and completing the local Room transaction, in the same lock order
as consent/revocation. DeliveryWriter receives that account for both CREATE and UPDATE.
The account is never copied from an old operation, nor inferred from a remote receipt.

This is LOCAL intent attribution, not upload authorization or a network refresh. Cached
non-simulated identity can attribute offline writes for a consented farm; absent/broken/
unconfigured identity, another account, revoked consent and unconsented farms stay local.
Network freshness, issuer/permissions and consent must still be verified before dispatch.
Existing account-less historical rows are never adopted just by login or consent.

The recovery fixture now uses fake Auth TRANSPORT but real AccountRepository,
LocalFarmLinkRepository, durable consent/backup and DeliveryRepository.create/update.
Only the network failure status/attempt count is injected. There is no manual account_id
assignment in that positive flow. Additional Room cases cover unconsented creation,
legacy non-adoption, logout, account B, revocation and local kilos preserved.
Default local-only construction and dormant OCR paths remain unbound.

## P2 — ACK after revocation (OPEN, not fixed)

Decision: revocation must NOT unblock the old operation or authorize a new dispatch.
A new Room regression asserts a late ACK is rejected, BLOCKED remains, and local kilos
and remote metadata are untouched. This proves safe rejection, not remote convergence.
The applied remote version can still remain unknown locally: an immutable receipt journal
and explicit authenticated reconciliation at re-consent are required before sync activation.
No claim that the version divergence or re-consent workflow is implemented is made here.

## P3 — other aggregates (OPEN)

The new APIs remain Delivery-only. Do not route DELETE, expenses or attachments through
these rules without their own outcome recovery, attribution and permission tests.
