# G2.4 — Snapshot local completo de Pesada (v2)
Fecha: 2026-10-23. Preparación local; sin transporte ni despliegue.

## Motivo
El formato v1 solo incluía DeliveryEntity. Una edición que cambiaba exclusivamente el reparto entre parcelas no cambiaba el JSON y podía reutilizar el UUID pendiente. Tampoco conservaba destinationOrganizationId.

## Formato y escritura
DeliveryWriter crea intentos payloadVersion=2 después de guardar los hijos dentro de la misma transacción. Añade destinationOrganizationId cuando existe y parcels ordenado por parcelId UUID.
Cada hijo conserva id, parcelId, campaignParcelId (nullable), parcelNameAtDelivery, weightGrams (nullable) y allocationMode. No incluye timestamps para evitar cambiar la huella por datos de auditoría; no inventa kilos desconocidos.
enqueueCollapsed incluye payloadVersion entre las condiciones para reutilizar UUID. Intentos previos FAILED/PROCESSING/BLOCKED se conservan como antes.
La comparación local de ACK usa los hijos actuales; un reparto cambiado no se considera sincronizado por un ACK de otro snapshot.

## Compatibilidad y límite obligatorio
El RPC remoto actual solo representa cabecera. NO enviar v2 a ese RPC: podría ignorar los hijos y producir una confirmación incompleta.
verifiedRecoveredDeliveryReceipt solo admite v1; rechaza v2 incluso con un predicado de hash inyectado. El helper de hash plano no se amplía a arrays en este cambio.
Antes de habilitar v2 deben existir contrato servidor completo con validación de pertenencia finca/workspace/campaña, almacenamiento/restore de hijos y organización, hashes compartidos para arrays/null, versionado del recibo, bootstrap de dependencias y pruebas nativas A/B/idempotencia/concurrencia.
La función local applyConfirmedDeliveryReceipt sigue siendo una primitiva transaccional: su llamador debe aportar una confirmación de un contrato que soporte la versión exacta. No existe worker ni autoridad de envío en esta PR.

## Pruebas añadidas
- Editar solo pesos por parcela conserva el total, cambia snapshot y UUID.
- Orden determinista y datos históricos presentes.
- Peso sin reparto permanece null y UNALLOCATED.
- Recuperación v2 rechazada por el verificador remoto actual.
CI del nuevo HEAD pendiente; estas pruebas no acreditan sincronización completa.
