# G2.4 — Puerta local de confirmación (sin red)

**Fecha:** 22-10-2026  
**Base:** PR #766 (`feature/g2.3-offline-first-room`), sin fusionar  
**Seguimiento:** issue #767  
**Alcance:** solo recepción/validación de ACK y preservación offline de pesadas; no incluye llamadas HTTP, autenticación de red, despliegues, subida, ni APK candidata.

## Contrato implementado

`DeliverySyncReceipt` incluye `operationId`, `deliveryId`, `farmId`, `accountId`, `payloadJson` **idéntico al intento persistido** y `remoteVersion` recibido del servidor.

`MaginaOlivoDatabase.applyConfirmedDeliveryReceipt` funciona en una sola transacción Room:

1. Busca un intento real en la cola y valida identificador, entidad `DELIVERY`, operación `CREATE/UPDATE`, cuenta, finca, snapshot JSON inmutable y versión positiva. Un registro `BLOCKED`, de cuenta/finca incorrecta o sin `accountId` queda rechazado.
2. Un segundo ACK de un intento `CONFIRMED` no toca la pesada actual: es idempotente localmente.
3. Comprueba la pesada y la foto del snapshot lógico desde el mismo serializador que guarda `DeliveryWriter`. Nunca usa la versión local como `baseVersion` remota.
4. Si la pesada sigue siendo exactamente la misma y no hay operaciones rivales, marca el intento `CONFIRMED` y actualiza **solo metadatos** `remoteVersion`, `lastSyncedAt` y `SyncStatus.SYNCED`.
5. Si ha cambiado la pesada, hay otros intentos sin resolver o la versión remota local es más reciente, deja los kilos, fecha, campaña, campos, adjuntos y versión local sin cambios; marca el intento como `CONFIRMED`, bloquea los intentos rivales y pone `SyncStatus.CONFLICT` para reconciliación explícita. No intenta subir el estado nuevo por sí mismo.
6. Los `CONFIRMED` ya no cuentan como `CREATE` sin resolver al editar la pesada: la siguiente edición local, una vez confirmada, pasa a `UPDATE` con `baseVersion` real.

La inclusión de `CONFIRMED` en el enum `OutboxStatus` no cambia columnas ni índices Room; se persiste como texto ya admitido. No se ha alterado el esquema 27 ni añadido migración.

## Pruebas incorporadas

`DeliveryContractTest`:
- ACK correcto conserva campos, versión y `updatedAt`, registra `remoteVersion`, repite idempotentemente y una edición posterior crea `UPDATE`.
- ACK tardío de un intento `PROCESSING` al haberse editado una pesada deja el dato nuevo intacto y bloquea la operación posterior.
- Deniega ACK con cuenta, finca, payload o versión inválida sin modificar datos.

## Límites y condiciones para la fase siguiente

- Esta puerta **NO autoriza envío**. El futuro trabajador de red debe validar identidad activa de Supabase, ledger G1b persistido y autorización del servidor justo antes de enviar. La mayoría de intents agrícolas heredados carecen de `accountId`: son estrictamente locales.
- Una respuesta HTTP no es suficiente si se perdió la confirmación: `check_sync_operations` debe devolver no solo el ID confirmado sino la **versión de ese intento**, almacenada inmutable en G2.1. No inventar `remoteVersion` mirando la fila remota actual; una versión posterior no es el ACK de una operación antigua.
- Se necesita un protocolo deliberado `ACK → rebase → nuevo operation UUID` para los `BLOCKED`; esta implementación **solo pone en cuarentena**, no resuelve divergencias.
- No se resuelven todavía `DELETE` de pesadas, permisos multirol, adjuntos, gastos, bootstrap de `workspaces/farms/campaigns`, versiones base de otras entidades, ni operación cruzada entre cuentas. No despachar esas clases.
- Los fallos de Gate 3 que ya aparecían en `AppNavigationTest` siguen siendo bloqueantes hasta que un SHA válido complete la suite.
- No fusionar la PR de G2.4 antes de integrar y verificar G2.3; no desplegar a DEV persistente o producción sin permiso y migraciones/RLS revisados.
