## 1. Estado Real de G2.3 y PR #766

La fase G2.3 implementa la cola de operaciones persistente local en Android (Room) garantizando:
- Reutilización de la infraestructura existente (`SyncOutboxEntity`, `SyncOutboxDao`, `OutboxWriter`, `DeliveryWriter`).
- Migración Room 26 → 27 con esquema exportado y versionado (`27.json`).
- Serialización canónica de payloads en formato JSON para inserción y actualización de pesadas (`DeliveryWriter`).
- Reglas estrictas de inmutabilidad de identificadores de operación: se conserva el `operation_id` en reintentos idempotentes idénticos; se genera un nuevo UUID ante cualquier mutación del payload, cuenta o versión base para prevenir alteraciones en vuelo.
- Diferenciación estricta de versiones: nunca se usa la versión local como sustituto de `remoteVersion` confirmada por el servidor.
- Respeto integral al consentimiento G1b: las operaciones sobre fincas revocadas se transicionan atómicamente a `BLOCKED` (abarcando estados `PENDING`, `FAILED` y `PROCESSING`).
- Preservación de operaciones `FAILED`: no se eliminan al colapsar nuevas operaciones locales.
- Las escrituras agrícolas locales se persisten sin importar el estado de consentimiento o sesión de cuenta (offline-first).

## 6. Actualización 22/10/2026 — Integridad de consentimiento y cuarentena offline

**Estado real:** PR #766 sigue en DRAFT. No hay sincronización HTTP, fusión a `main`, despliegue de Supabase ni APK candidata. Esta sección **sustituye** los pendientes originales de revocación indicados arriba, que describen una versión anterior de la rama.

### Implementado en esta sesión

- `AndroidFarmLinkLedger.kt` y `FarmLinkConsent.kt`: eventos de revocación locales inmutables, compatibles con los consentimientos G1b anteriores. Se preserva el historial completo, y `activeFarmIds` excluye fincas revocadas; el archivo está protegido por validación de hash y escritura atómica.
- `LocalFarmLinkRepository.kt`: se registra la revocación durable **antes** de bloquear operaciones de Room; se relee el ledger actual antes de comprobar `isFarmConsented`, incluso cuando otro repositorio lo haya cambiado. Fallos al leer el ledger deniegan acceso. Una finca revocada no se reactiva automáticamente.
- `FarmLinkPanel.kt`: el agricultor ve la finca revocada como tal, y no se interpreta como selección nueva o autorización de envío.
- `FarmLinkRepositoryTest.kt`: regresiones sobre revocación repetida, reinicio/reapertura del ledger y lectura obsoleta entre instancias.
- `SyncOutboxDao.kt`: `listReadyForAccount` y `observeReady` no presentan ninguna operación de un agregado cuando hay **otra** operación del mismo `entity_type + entity_id` con estado `PENDING`, `FAILED`, `PROCESSING` o `BLOCKED`, incluso si la otra cuenta es distinta. Se conservan todas las filas; no se suprimen intentos sin conocimiento del servidor.
- `FarmLinkRepositoryTest.kt`: prueba de cuarentena de una pesada con `FAILED + PENDING`, `PROCESSING + PENDING` y `BLOCKED + PENDING` frente a una pesada independiente que sí sigue disponible.

### Hallazgos reales de CI

- El commit `49c29c2` corrigió el import de `assertFalse`, y la compilación `foundation` de GitHub Actions se comprobó aprobada.
- En el Gate 3 de ese commit se ejecutaron **834 pruebas**, con **una fallida** por `RootViewWithoutFocusException` de Espresso en `AppNavigationTest.centralAddIsAButtonAndCancelsOnEveryRootWithoutNavigation`. No ocultar ni marcar Gate 3 en verde; el motivo puede ser intermitente, pero no está demostrado que sea exclusivamente infraestructura.
- Los commits posteriores que incorporan las revocaciones persistentes y la cuarentena necesitan el resultado **del propio HEAD** para considerarse validados. Consultar `GitHub Actions` sobre la PR #766; no reutilizar el verde de otro SHA.

### Condiciones obligatorias antes de G2.4 (sin activación todavía)

1. La cuarentena no equivale a reconciliación. Si el servidor llegó a aplicar una operación `FAILED`/en vuelo, consultar `check_sync_operations` y usar la **`remote_version` del ACK de esa operación**. Reescribir de manera atómica un snapshot posterior como UPDATE con `baseVersion` confirmado y UUID **nuevo**, sin volver a enviar el viejo CREATE a ciegas. Si no puede resolverse inequívocamente, dejar el agregado bloqueado e informar del conflicto.
2. Los envíos HTTP deben volver a validar **en el último instante**: identidad autenticada, consentimiento local persistido y aún activo, propietario/grant válido en servidor, `account_id` coherente, `farm_id` coherente, y snapshot JSON inmutable del ID de operación elegido. Nunca inferir permiso de `listReadyForAccount()` únicamente.
3. En una cola con operaciones de una misma entidad asociadas a distintas cuentas, congelar el agregado hasta aclarar la identidad; jamás migrar o reasignar operaciones silenciosamente.
4. Separar claramente intentos legados sin `account_id`/`farm_id`/`payload_json`: permanecen locales hasta autorización explícita y bootstrap verificado.
5. Confirmar tablas dependientes (`workspace`, `farm`, `campaign`) antes de enviar pesadas. No desplegar el SQL experimental de G2.1 directamente a DEV persistente o a producción; probar migraciones y RLS primero.
6. Resolver por separado el comportamiento de DELETE de pesadas: el borrado local actual aún no empaqueta payload/binding remotos, por tanto no está listo para una llamada RPC. No borrar remotamente de forma implícita.
7. Exigir pruebas reproducibles de caída entre envío/ACK, replay idempotente, cambio de cuenta, revocación, conflictos 409, y que los datos locales se conservan bajo pérdida de red y tras reinicio.
