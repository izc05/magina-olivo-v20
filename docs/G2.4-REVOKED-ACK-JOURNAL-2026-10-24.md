# P2 — durable ACK evidence after revocation

## Scope

This slice supplies the storage primitive and its contract. It does not install an HTTP
worker, an Android journal factory, re-consent UI or authenticated reconciliation. P2 is
not closed by the existence of this file or by the standalone JVM tests.

`DeliveryReceiptJournal` stores one immutable prepared operation plus its historical
receipt in a private no-backup file, separate from the operational Room row. It never
promotes BLOCKED, changes kilos/remote metadata, grants consent or authorizes dispatch.
The checksum detects corruption; it is not authentication of a server response.

## Required ordering for the future receiver

1. Under current dispatch/account/consent protections, verify the exact outbox operation
   and prepare its actor/issuer, local and remote workspace, consent ID/text version,
   farm, operation/delivery IDs, payload version/hash and base version BEFORE HTTP.
2. Verify the authenticated response against that previously prepared scope and exact
   operation. Do not derive a new actor or destination from the current session or callback.
3. Record the receipt before attempting any Room acknowledgement. The stored version is
   the historical version of this operation, not a subsequent version of the remote row.
4. If consent was revoked or the account changed, leave the operational row BLOCKED and
   do not issue another request. Keeping private evidence of an already completed request
   does not grant access to it from another account or give permission for a new send.
5. After a crash, reopening a committed receipt preserves it. If publication did not occur,
   the pending prepared scope remains: query the authenticated result by the same UUID or
   retry the same immutable operation only when authorization and consent allow it.

`prepare` cannot replace a previous identity, destination, consent or snapshot. An exact
`record` replay is idempotent; a different remote version for the same operation is
rejected without replacing the receipt. An ACK cannot create its own preparation.

## Persistence

JVM synchronization plus an OS lock serialize each file across instances/processes.
Bounded, strictly decoded UTF-8 and a framed SHA-256 checksum detect invalid/truncated
records. A synced temporary is published by atomic rename; unsupported atomic moves fail
without a non-atomic fallback. Only published receipts are durable commits. Before rename,
the earlier pending record is retained; the prepared operation enables remote result recovery.
Orphan temporary cleanup is limited to this journal's exact prefix and canonical UUID suffix.
Device power-loss resistance is not claimed: directory fsync is not implemented.
