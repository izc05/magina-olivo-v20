**HEAD Android:** `b155811f` (PR #774, DRAFT). **Matriz:** #773, rama
`codex/g21-expense-farm-scope`, HEAD `11e8559b`.
Documento de diseño. **No habilita HTTP**, no despliega SQL y no toca identidades ni
consentimientos persistidos.

## 1. La única costura que falta implementar

G2.4 dejó el lado local completo detrás de tres puntos de entrada de producción en
`LocalFarmLinkRepository`, todos sobre `withServerVerifiedIdentity`:

- `prepareDeliveryForDispatch(...)` — escribe el PREPARE duradero y reclama la operación.
- `recordAuthenticatedDeliveryAck(...)` — correlaciona el recibo y aplica o retiene.
- `settleInterruptedDeliveryDispatches(...)` — recuperación tras cierre forzado.

Y la lectura remota entra por una sola función inyectada
(`LocalFarmLinkRepository.kt:130`):

```kotlin
lookup: suspend (AuthSession) -> RemoteDeliveryState
```

```kotlin
internal data class RemoteDeliveryState(
    val operationReceipt: RecoveredDeliveryReceipt?,
    val headVersion: Long?,
    val headPayloadHash: String?,
)
```

**Por tanto el trabajo de integración es un adaptador que rellena `RemoteDeliveryState` y
nada más.** No hay que modificar Room, el lease, el ledger ni la aplicación transaccional.

## 2. Adaptador de lectura y ACK — contrato exacto

### 2.1 `operationReceipt` ← `check_sync_operations`

`POST /rest/v1/rpc/check_sync_operations` con `apikey` pública y
`Authorization: Bearer <access_token>` de la sesión verificada. Lotes de **hasta 200**
`operation_ids`. Del campo `confirmed_receipts[]` se construye, por operación:

| Campo de `RecoveredDeliveryReceipt` | Origen | Regla |
| --- | --- | --- |
| `operationId` | `operation_id` del recibo | Debe ser el **mismo UUID** que la operación local. No se genera uno nuevo nunca. |
| `deliveryId` | `entity_id` | Debe igualar `operation.entityId`. |
| `entityType` | `entity_type` | Se traduce a `SyncEntityType`. Si no es `DELIVERY`, el recibo se descarta. Sin valor por defecto: el adaptador declara lo que leyó. |
| `accountId` | **la sesión verificada**, no el JSON | El servidor deriva el actor de `auth.uid()` y no lo devuelve. Rellenarlo desde la respuesta sería aceptar identidad enviada por el cliente. |
| `remoteVersion` | `remote_version` | ≥ 1. Para `UPDATE` debe ser > `baseRemoteVersion`. |
| `payloadHash` | `payload_hash` | 64 hex minúsculas. Se compara contra `deliveryPayloadHash(payloadJson, payloadVersion)` sobre los **bytes UTF-8 exactos persistidos**, nunca sobre un JSON reserializado de la lectura. |
| `payloadVersion` | `payload_version` | Debe ser 2 para la pesada v2 e igualar `operation.payloadVersion`. |

Todas estas comprobaciones ya están implementadas y probadas en
`verifiedRecoveredDeliveryReceipt`; el adaptador solo debe **no saltárselas**.

Reglas que la matriz impone y el adaptador debe respetar:

- El recibo es el **histórico de esa operación**, aunque el agregado tenga una versión
  posterior. No es el HEAD.
- Otra cuenta recibe lista vacía. **La ausencia de recibo no prueba que el envío falló**:
  se traduce en `operationReceipt = null`, nunca en «fallido».

### 2.2 `headVersion` / `headPayloadHash` ← `get_own_delivery_v2`

`get_own_delivery_v2(p_delivery_id)` → `delivery.version` y `head_payload_hash`.
`head_payload_hash` es `null` si no existe una coincidencia **única** de una operación
`DELIVERY` del mismo actor en la versión actual. En ese caso, y ante cualquier
discrepancia de versión o hash, Android **mantiene conflicto o bloqueo** y no marca la
pesada como sincronizada. Eso es exactamente lo que hace hoy
`reconcileHeldDeliveryReceipt` devolviendo `REMOTE_CONFLICT`.

### 2.3 Traducción de errores

| Código PostgreSQL | HTTP | Resultado local |
| --- | --- | --- |
| `23505` | 409 | Conflicto. El PREPARE se conserva; la operación no se duplica. |
| `42501` | 403 | Acceso denegado con JWT válido → `NOT_AUTHORIZED`. No se reintenta en bucle. |
| `22023` | 400 | Payload rechazado → `REJECTED`. El payload no se modifica para «arreglarlo». |

Una respuesta HTTP por sí sola **no sustituye** la escritura duradera del recibo local.

## 3. D1 — issuer real del JWT: estado y plan de resolución

### Lo que ya coincide

| Lado | Valor |
| --- | --- |
| Matriz #773, candidato canónico | `https://zubpicdibqbmewxeurhm.supabase.co` |
| Android, proyecto DEV fijado en `AccountAuthDevConnectivityTest` | `zubpicdibqbmewxeurhm` |
| Android, `BuildConfig.AUTH_PROJECT_URL` (flavor dev) | se inyecta desde `MAGINA_AUTH_DEV_URL` y se valida con `^https://[a-z]{20}\.supabase\.co$` |
| Sujeto persistido en Android | `AUTH_PROJECT_URL + "|" + userId`, literal |
| Producción | `AUTH_PROJECT_URL` vacío |

**No hay discrepancia de valor entre Android y la matriz.** D1 no es un desajuste de
configuración de Android.

### M1 ejecutado — issuer declarado por el proyecto DEV

Lectura anónima, sin sesión y sin credenciales, el 2026-10-25 08:44 UTC:

```
GET https://zubpicdibqbmewxeurhm.supabase.co/auth/v1/.well-known/openid-configuration
HTTP 200
"issuer": "https://zubpicdibqbmewxeurhm.supabase.co/auth/v1"
```

Coincide **literalmente** con `AUTH_PROJECT_URL + "/auth/v1"`. Resultado: coincidencia
exacta, sin barras extra, sin HTTP y sin cambio de mayúsculas.

JWKS del mismo proyecto, también anónimo: **una** clave, `kty=EC`, `alg=ES256`, `use=sig`,
`kid=994537d8-aae1-42bd-bd1f-a647a6c7be49`. Los tokens son asimétricos, no HS256 con
secreto compartido, de modo que la verificación en servidor debe hacerse contra JWKS por
`kid` **y además** comparar el issuer literalmente.

**Límite de lo que M1 prueba:** el campo `issuer` del descubrimiento OIDC es lo que el
proyecto **declara**; no es el claim `iss` de un `access_token` real de GoTrue. Es
evidencia fuerte y necesaria, pero no sustituye a M2.

### Lo que falta de verdad

1. **M2, aún sin medir.** Nadie ha observado el claim `iss` literal de un `access_token`
   de Auth DEV. El issuer HTTPS de la suite nativa es **sintético**, porque GoTrue local
   emite HTTP. La comparación requerida es literal:
   `iss == AUTH_PROJECT_URL + "/auth/v1"` y `receipt.issuer == AUTH_PROJECT_URL`.
   Sin credenciales de una cuenta exclusiva de pruebas en DEV no se puede ejecutar.
2. **Defecto en el SQL propuesto (lado servidor, de Codex).** La expresión regular actual
   de G1c acepta **cualquier** host HTTPS con `/auth/v1` y no lo compara con la URL del
   proyecto esperado. Un JWT firmado por la clave de confianza pero con `iss` ajeno pasaría.
   La firma del gateway y la comparación en el cliente **no sustituyen** una vinculación
   exacta del issuer en el servidor.
3. En esta máquina no existe `local.properties` ni `~/.gradle/gradle.properties`, así que
   ni el flavor dev lleva hoy un `AUTH_PROJECT_URL` real ni el test de opt-in puede
   ejecutarse sin credenciales.

### Reparto propuesto

**Codex (servidor, dentro de D1, antes de desplegar G1c):**

- Sustituir la regex permisiva por una **fuente de configuración del issuer permitido por
  entorno**, y comparar `iss` contra ella de forma literal.
- Añadir una prueba que **rechace** un JWT firmado por la clave de confianza con `iss` de
  otro proyecto. Hoy ese caso no está cubierto.

**Claude (Android), bajo autorización expresa y en este orden:**

- Paso M1: **ejecutado y en verde**, ver arriba. Coincidencia literal del issuer declarado.
- Paso M2, con una cuenta de pruebas DEV: iniciar sesión, decodificar el payload del
  `access_token` y validar el token contra `/auth/v1/user`. Registrar el `iss` literal
  observado. Es la medición que la matriz exige y que hoy nadie ha hecho.
- Si M1 o M2 revelan otro issuer, **detener el envío**. No normalizar en el cliente.

### Regla de seguridad sobre datos ya persistidos

Si un dispositivo ya guarda otro sujeto: conservar Room, adjuntos, backups, ledger y
operaciones pendientes **sin cambiar sus bytes**; inventariar por sujeto y distinguir
operaciones nunca enviadas de operaciones con resultado incierto. Solo tras probar que es
**la misma cuenta del mismo proyecto**, una migración local versionada y reversible, con
copia íntegra, selección explícita de fincas y **consentimiento nuevo** por finca. Nunca
reetiquetar automáticamente recibos, reservas u operaciones posiblemente enviadas. Hoy no
existe ninguna migración aprobada y yo no la ejecutaré sin un plan revisado.

## 4. Plan mínimo del primer ensayo: una pesada sin fotografía, con respuesta perdida

Finca, parcela y campaña **preparadas de antemano** (su creación completa desde Android es
un ensayo posterior).

| Paso | Acción | Comprobación |
| --- | --- | --- |
| 0 | Verificar D1 (M1 y M2). Sesión DEV verificada, consentimiento vigente para esa finca. | `iss` literal confirmado. Sin esto, no se continúa. |
| 1 | Crear offline una pesada identificable, **sin adjunto**, con `weightGrams` reales por parcela. | La pesada existe en Room con `syncStatus` pendiente. |
| 2 | `prepareDeliveryForDispatch` | Fila en `delivery_dispatch_prepare` con identidad, consentimiento, `payload_hash` y `lease_marker`; operación `PROCESSING`. |
| 3 | `sync_own_delivery_v2(p_operation_id, p_delivery)` | Se envía el payload exacto ya hasheado. |
| 4 | **Cortar la respuesta después del commit del servidor** (modo avión en cuanto se envía). | Android no sabe el resultado. El UUID y el payload no cambian. |
| 5 | Cierre forzado de la app y reapertura. | `settleInterruptedDeliveryDispatches` deja la operación en `OUTCOME_UNKNOWN`, **no terminal**. |
| 6 | Restaurar red. `check_sync_operations([operationId])` | Llega el recibo histórico del **mismo UUID**. |
| 7 | `recordAuthenticatedDeliveryAck` | Se aplica **exactamente una vez**: `syncStatus = SYNCED`, kilos y parcelas intactos, sin duplicado. |
| 8 | `get_own_delivery_v2(deliveryId)` | `version` y `head_payload_hash` coinciden con el recibo aplicado. |
| 9 | Repetir los pasos 6–8 **con otra cuenta**. | Lectura y ACK denegados; lista vacía. Ningún dato cruzado. |

Criterio de éxito: ni pérdida ni duplicado, kilos exactos, un solo UUID de operación de
principio a fin, y el recibo escrito de forma duradera antes de cualquier cambio de estado
de la pesada.
