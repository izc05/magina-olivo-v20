# G1c Android journal recovery — preparation

Branch `test/g1c-android-journal-recovery`, based on G1c `7cb31d3b`. This is an independent, dependent DRAFT QA slice. No app consumer, Context factory, Auth integration, sync, HTTP, Room, schema, migration or production source changes.

The instrumentation class `G1cJournalProcessTest` exposes methods `holdAtCheckpoint` and `recoverAfterForceStop`. Ordinary suites skip both without `qaG1cJournalProcess=true`. Required arguments are canonical UUID `qaG1cJournalToken` and checkpoint `qaG1cJournalCheckpoint`: `prepared`, `receipt-before-rename`, or `receipt-committed`. DEV package and QEMU are checked before creating files.

Each run writes only synthetic files under private `files/g1c-journal-process/TOKEN/CHECKPOINT`. The writer rejects an existing directory. It uses the real DurableReservationJournal, fixed synthetic A/B actors and request/receipt values, and a counted beforeCommit callback. A durable marker records checkpoint, writer PID and the SHA256 of the currently committed journal. The writer waits at the exact selected boundary for up to60seconds; normal return is an assertion failure. Root's harness owns the actual force-stop and starts recovery without clearing app data.

Boundary expectations: after prepare the committed snapshot is pending; during receipt commit's second beforeCommit callback the temporary receipt bytes have been synced but journal.bin is still pending; after receipt commit the exact receipt is RESERVED_REMOTE. Recovery requires a different PID and byte-identical main journal hash from the marker before reading it. It checks expected request/status/receipt, B scope isolation, B-visible no-send/no-write, same-operation lost-response retry for pending states, exact A receipt persistence, duplicate replay without transport or byte changes, and a separate delayed-ack operation becoming AWAITING_ACTOR under B without permitting a B send. All transports are synthetic in-process objects.

Evidence is copied only from this synthetic checkpoint directory into externalFilesDir/g1c-journal-process-evidence/TOKEN/CHECKPOINT. Exact exported names are marker.txt, journal-before.bin (main bytes on reopen), journal-after-b.bin (after B's blocked attempt), journal-after-a.bin (confirmed/replayed A receipt), and result.txt (contains `PASS checkpoint=CHECKPOINT` only after all checks). Before and after-B must compare byte-identically; before's SHA256 must match the marker. Result also records errors and elapsed time. Available partial evidence is exported on failure without replacing the original exception. No user state is cleared, imported, restored or deleted. Atomic-move or file-lock failure remains a failure; there is no fallback adapter. This demonstrates Android process termination boundaries, not power-loss durability. It complements the existing JVM three-boundary process test and isolated PostgreSQL tests; it cannot replace them or complete G1.

The focused harness runs the writer as a background adb child, waits up to30seconds for a complete private marker, validates its checkpoint/PID/hash against the live DEV process, force-stops only DEV, and bounds the client exit wait to10seconds. Writer adb exit0 is never treated as a passing writer test. Recovery output, logcat and all five files are retained before checking JUnit/adb status, marker SHA256 and byte equality. No app-data clear is used. Its exit trap cleans up only its own client and guarded DEV process.

Static validation completed: Bash syntax; shared disposable-device guards6/6; nine fake-adb cases covering three live-until-stop writers, zero-exit JUnit failure, premature writer exit, missing evidence, failed pull, missing opt-in, physical serial, invalid UUID and post-stop pidof transport timeout. Process disappearance requires pidof exit1 with empty stdout; exit124/other transport errors fail before recovery, with exit code and stderr retained. The fake success case produces3PASS, while all failure cases remain nonzero. Local Gradle/emulator execution is excluded because of disk constraints. Compilation and actual Android force-stop outcomes remain pending remote CI.
