## Changes

- `claimFailedDeliveryForRecovery` atomically claims a FAILED Delivery while newer,
  unattempted same-account/same-farm PENDING snapshots wait. It preserves operation UUID,
  payload and base version; two connections cannot claim the same operation. Unknown,
  blocked, already attempted or cross-account siblings prevent recovery. No age-based
  takeover of PROCESSING is implemented: an old timestamp is not proof a request ended.
- Existing receipt processing keeps recording the confirmed operation and quarantining
  later snapshots. These quarantines now carry `NEEDS_REBASE`, distinguishable from
  revoked or unrelated blocked work.
- `rebaseConfirmedDeliveryEdit` provides the explicit next local transaction: authenticated
  receipt plus authenticated remote-head version/hash and fresh authorization callback
  are required inputs. It accepts only v2 snapshots, same account/farm, a live delivery,
  and unattempted snapshots quarantined by receipt processing. The new UPDATE has a new
  UUID and uses the receipt version, not a constant. Repeating an identical reconciliation
  preserves the new operation. Confirmed/attempted intents are never deleted.
- A remote head advanced from receipt version 7 to 8, a hash mismatch, identity mismatch,
  denied consent, deleted record or attempted sibling cannot trigger an overwrite.
  A future server CAS also remains mandatory for edits after observation.

## Remaining scope

This is a local recovery API, not a running sync service. No Auth session, durable consent,
HTTP, remote observation or background worker is fabricated by these methods. Instrumented
authorization callbacks and explicit SQL account binding are synthetic test fixtures.
The real sender must obtain authenticated observations, coordinate identity and revocation,
recheck authorization before HTTP, and retain server CAS/idempotency checks.

Safe process-death recovery of PROCESSING still requires a worker ownership protocol and
real process-death evidence. SQLite reopen is not a process kill. No remote DELETE,
expense/attachment dispatch, schema migration, Supabase deployment, main merge or release
candidate is introduced. G2.4/G2 remain open until the applicable gates actually pass.
