## A. Qué queda cerrado

G2.4 absorbe íntegramente G2.3. La secuencia contratada es:

1. **PREPARE duradero antes de HTTP.** Antes de cualquier intento de red se escribe una
   fila en `delivery_dispatch_prepare` con la identidad completa del envío: operación,
   pesada, finca, cuenta, `issuer`, `subject = issuer|userId`, workspace local y remoto,
   consentimiento (operación y versión de texto), `payload_version`, `payload_hash`,
   `base_remote_version` y el marcador del lease vivo. La misma transacción reclama la
   operación del outbox.
2. **Correlación del ACK autenticado.** Un recibo solo se aplica si existe su PREPARE y
   coincide campo por campo. Sin PREPARE no hay aplicación posible; con PREPARE de otros
   bytes, otra finca u otro consentimiento, el resultado es `PREPARE_MISMATCH` y no se
   escribe nada.
3. **Aplicación o retención como prueba.** Con consentimiento vigente el ACK se aplica
   exactamente una vez. Con revocación posterior el recibo se retiene como evidencia
   (`HELD_AFTER_REVOCATION`) y la pesada no se toca.
4. **Lease y recuperación.** `DeliveryDispatchLease` usa un `FileLock` del sistema
   operativo sobre `delivery-dispatch.lock`. Tras un cierre forzado, solo el titular del
   lock de la misma época puede liquidar la operación interrumpida, y lo hace como
   `OUTCOME_UNKNOWN`, que es un estado **no terminal**: admite todavía su ACK tardío.

### Campos inmutables y campos que sí cambian

La identidad del ámbito preparado es inmutable una vez escrita. Tres columnas no forman
parte de esa identidad: `settled_at` y `settled_outcome` registran el resultado, y
`lease_marker` sigue al titular **actual**, porque un reintento después de un cierre
corre bajo una adquisición nueva y la recuperación compara la época viva contra ella.

## B. Garantías verificadas por prueba

Todas las pruebas de esta sección se ejecutaron en rojo antes de su corrección cuando
documentan un defecto, y en verde después.

| Garantía | Prueba |
| --- | --- |
| Un ACK sin PREPARE duradero nunca se aplica | `g24AnAckWithoutADurablePrepareRecordIsNeverApplied` |
| El PREPARE graba identidad, consentimiento y bytes, y reclama la operación | `g24PrepareRecordsIdentityConsentAndImmutableBytesAndClaimsTheOperation` |
| El PREPARE nunca sustituye un registro que describe otros bytes | `g24PrepareNeverReplacesARecordThatDescribesOtherBytes` |
| Una finca revocada nunca se prepara para envío | `g24ARevokedFarmIsNeverPreparedForDispatch` |
| Un ACK consentido y correlacionado se aplica exactamente una vez | `g24AConsentedCorrelatedAckIsAppliedExactlyOnce` |
| Un ACK de otros bytes u otra finca es discrepancia y no escribe nada | `g24ACorrelatedAckForOtherBytesOrAnotherFarmIsAMismatchAndWritesNothing` |
| Un ACK tras revocación se correlaciona, se retiene y deja la pesada intacta | `g24AnAckAfterRevocationIsCorrelatedThenHeldAndTheDeliveryIsUntouched` |
| Un recibo retenido congela esa pesada y bloquea un PREPARE nuevo | `g24PrepareIsRefusedWhileAHeldReceiptFreezesThatDelivery` |
| Un envío preparado e interrumpido solo lo liquida el titular del mismo lock | `g24AnInterruptedPreparedDispatchSettlesAsUnknownOnlyForTheSameLockOwner` |
| `NEEDS_REBASE` con revocación y sin recibo es su propio resultado terminal | `g24NeedsRebaseWithARevocationAndNoReceiptIsItsOwnTerminalOutcome` |
| La reconciliación exige el lease y la misma cuenta de principio a fin | `g24ReconciliationNeedsTheLeaseAndTheSameAccountThroughout` |
| `OUTCOME_UNKNOWN` admite todavía su ACK tardío, una sola vez | `g24ParityAnUnknownOutcomeStillAcceptsItsLateAckExactlyOnce` |
| `OUTCOME_UNKNOWN` se reintenta con la misma operación y los mismos bytes | `g24ParityAnUnknownOutcomeCanBeRetriedWithTheSameOperationAndBytes` |
| Un re-PREPARE rechaza un workspace remoto o una versión de consentimiento distintos | `g24ParityRePrepareRejectsAChangedRemoteWorkspaceOrConsentTextVersion`, `g24ParityRePrepareRejectsADifferentConsentTextVersion` |
| Dos cierres consecutivos (A→B→C) conservan el marcador vivo y siguen recuperables | `g24ParityTwoConsecutiveCrashesKeepTheLatestLeaseMarkerAndStayRecoverable` |
| La recuperación nunca sobrescribe una operación bloqueada que ya tiene su recibo | `g24ParityRecoveryNeverOverwritesABlockedOperationThatAlreadyHasItsReceipt` |
| Una interrupción entre el recibo y el outbox no deja medio estado | `g24ParityAnInterruptionBetweenTheReceiptAndTheOutboxLeavesNoHalfState` |
| Una transacción abandonada se revierte y una confirmada sobrevive a la reapertura | `g24ParityAnAbandonedTransactionIsRolledBackAndACommittedOneSurvivesReopening` |
| Texto mal formado, corrupción y truncamiento nunca pasan en silencio | `g24ParityMalformedTextCorruptionAndTruncationNeverPassSilently` |
| Dos emisores no pueden poseer el mismo envío; la recuperación exige el mismo lock | `g24ParityTwoSendersCannotOwnTheSameDispatchAndRecoveryNeedsTheSameLock` |
| Un recibo que declara otro `entity_type` nunca se adopta como esta pesada | `aReceiptThatReportsAnotherEntityTypeIsNeverAdoptedAsThisDelivery` (JVM) |

**Cobertura perdida, una y declarada:** `realProcessDeathPreservesThePublishedBoundaryAndExactRetry`

(`g24ParityTwoConsecutiveCrashesKeepTheLatestLeaseMarkerAndStayRecoverable`), que reproduce
la lógica de épocas de lease pero no la muerte real del proceso ni la concurrencia entre
procesos. Esa cobertura debe restituirse sobre Room antes de habilitar HTTP (sección D).

## D. Pruebas físicas pendientes — bloqueantes antes de habilitar HTTP

Estas tres son requisito previo a cualquier envío HTTP agrícola. Ninguna está ejecutada.

1. **Muerte real de proceso en cada checkpoint.** Matar el proceso de la app
   (`am force-stop` / `kill -9`) en cada punto: después del PREPARE y antes del envío;
   durante la espera de red; después del ACK y antes de aplicarlo. Verificar en cada caso
   que al reabrir se conserva el mismo UUID de operación, el mismo payload y el mismo
   hash, que el lease se recupera y que la operación queda `OUTCOME_UNKNOWN` y no perdida.
   Restituye la cobertura declarada perdida en la sección C.
2. **Concurrencia real entre procesos.** Dos procesos distintos del mismo paquete
   intentando el mismo envío a la vez, para comprobar que el `FileLock` del sistema
   operativo excluye de verdad, no solo dentro de una misma JVM.
3. **Revocación, caducidad y cambio de cuenta durante un envío en vuelo.** Revocar el
   consentimiento, caducar el token y cambiar de cuenta mientras hay una operación
   preparada, y comprobar que el recibo se retiene como prueba bajo su sujeto original.
