# G2.4 — Contrato verificable de recuperación de ACK perdido

Estado: especificación de integración; **NO implementa transporte HTTP, ni autoriza envíos, ni despliega SQL**.

## Fuentes de verdad
- Android Room: `sync_outbox`, con `operation_id`, `account_id`, `farm_id`, `payload_json`, `base_remote_version` y estado persistidos.
- Servidor G2.1: `check_sync_operations(UUID[])` devuelve `confirmed_receipts` con `operation_id`, `entity_id`, `entity_type`, `remote_version` (versión aplicada por **esa** operación) y `payload_hash`.
- Nunca usar la versión actual de `deliveries` para confirmar una operación histórica.

## Algoritmo de recuperación (futuro worker; no ejecutar en esta PR)
1. Capturar la cuenta autenticada y obtener **solo** operaciones locales con `account_id` idéntico. Excluir filas sin cuenta, finca o payload, y todos los estados `BLOCKED`.
2. Consultar `check_sync_operations` en lotes de hasta 200 IDs, con sesión válida. El resultado es evidencia de aplicación, **no** consentimiento para nuevas escrituras.
3. Para cada recibo, validar `operation_id`, `entity_id`, `entity_type=DELIVERY`, `remote_version > 0`, pertenencia a la cuenta activa y vínculo finca-cuenta. Comprobar `payload_hash` frente a los bytes exactos del snapshot inmutable local, con algoritmo y codificación probados contra el servidor. No aceptar un JSON reserializado como equivalente sin prueba.
4. Si falta cualquier dato, hay cambio de cuenta, revocación o hash no coincidente: **fallar cerrado**, preservar Room y registrar conflicto. No inventar versión ni marcar `CONFIRMED`.
5. Si coincide todo, llamar a `applyConfirmedDeliveryReceipt` con el snapshot persistido original y la versión de ese recibo. Esta función debe preservar kilos y demás campos locales.
6. Si el resultado es `NEEDS_REBASE`, mantener operaciones rivales bloqueadas. Recuperar historial de operaciones y construir una nueva operación con UUID nuevo y `baseRemoteVersion` confirmada **solo** después de reconciliación explícita.
7. Tras caída de proceso en cualquier punto, repetir el flujo debe ser idempotente. `ALREADY_CONFIRMED` no debe cambiar datos agrícolas.

## Matriz mínima de pruebas de integración
| Escenario | Resultado exigido |
| --- | --- |
| Servidor aplica CREATE; Android cae antes de recibir ACK | Consulta recupera versión del CREATE, confirma una vez |
| Repetir consulta y ACK | `ALREADY_CONFIRMED`, sin modificación de kilos ni versión local |
| Editar pesada mientras CREATE está en vuelo | ACK antiguo no pisa edición; nuevo snapshot queda bloqueado hasta rebase |
| Hash del payload distinto | Rechazo, sin confirmar |
| Recibo de otra cuenta o entidad | Rechazo, sin filtrar datos ajenos |
| Revocar consentimiento durante `PROCESSING` | Bloqueo durable; ningún envío posterior |
| Sin red / reinicio / sesión caducada | Datos locales intactos; no envíos |
| Respuesta 409 / versiones concurrentes | Conflicto explícito, no reintento ciego |
| Operación legada sin cuenta/payload/finca | Solo local; nunca despachada |
| 201 IDs y 0 IDs | Lotes acotados; resultado vacío seguro |
| Dos ACK históricos para la misma pesada | Cada operación conserva su propia `remote_version` |

## Bloqueo de interoperabilidad de hash (auditoría 22/10)

El SQL de G2.1 calcula `encode(sha256(convert_to(p_delivery::text, 'UTF8')), 'hex')` sobre un parámetro PostgreSQL **JSONB**. El texto de JSONB no es necesariamente idéntico a `payload_json` almacenado por Android. **No** sustituir el predicado `hashMatches` por SHA-256 directo del JSON original sin demostrar equivalencia; el contrato de bytes sigue pendiente.

Criterio de aceptación: vectores de prueba compartidos ejecutados en PostgreSQL real y Kotlin (orden de claves, Unicode, escapes, espacios, números, null) y decisión explícita sobre compatibilidad con recibos históricos. Ante divergencia, la recuperación debe rechazar el ACK sin tocar datos agrícolas. Referencia: comentario de auditoría en PR #768.
