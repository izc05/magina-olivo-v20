# Comparativa tecnológica y arquitectura multiplataforma

**Corte de investigación: 9 de noviembre de 2026.** Las valoraciones comparativas se marcan como **INTERPRETACIÓN** cuando derivan de características documentadas, y como **PENDIENTE** cuando necesitan datos del proyecto, pruebas propias o confirmación del proveedor. No se han supuesto volúmenes de transacciones, requisitos funcionales administrativos ni costes unitarios.

## Conclusión

**INTERPRETACIÓN — Recomendación provisional:** para una aplicación dirigida a miles de agricultores, con operación de campo sin conectividad fiable y clientes Android, iOS y web, la opción con mejor equilibrio inicial es **React Native + Expo + TypeScript para móvil**, una **aplicación web React separada** para escritorio/gestión si la experiencia web es prioritaria, un backend PostgreSQL administrado (Supabase es viable) y persistencia local SQLite con un protocolo explícito de sincronización. Compartiría esquemas, validaciones, reglas puras y clientes de API, no la interfaz ni la base de datos física de navegador/móvil. **No se recomienda entender “Expo + PostgreSQL/Supabase + SQLite” como una solución offline terminada**: SQLite resuelve almacenamiento local; no implementa por sí solo sincronización, resolución de conflictos, cola fiable de operaciones ni seguridad del backend. Expo reconoce que puede ser necesario construir una capa de sincronización propia y que las herramientas local-first siguen madurando. [1] [2]

**INTERPRETACIÓN:** si la prioridad máxima es experiencia móvil nativa, capacidades intensivas del dispositivo, soporte a largo plazo y Android como plataforma principal, Kotlin/Compose/Room reduce la distancia a Android, pero exige una app iOS y web con sus propios clientes y una estrategia de reutilización distinta. Flutter es la alternativa de un solo código de UI más coherente para Android/iOS/web si el equipo acepta Dart; no elimina diferencias de UX web ni el trabajo offline. React web + Capacitor resulta apropiado si el producto es ante todo web y el uso de funciones del teléfono es acotado. “Kotlin/RN híbrido” puede ser una opción gradual, no un atajo de coste: genera dos paradigmas móviles, puentes/integraciones y superficies de prueba.

## Qué significa comparar estas opciones

**VERIFICADO:** Room abstrae SQLite para Android, comprueba consultas SQL en compilación y ofrece migraciones; Android recomienda que los datos persistidos soporten funcionamiento cuando la red es intermitente o no disponible. [3] [4] **VERIFICADO:** `expo-sqlite` ofrece una base SQLite persistente entre reinicios de la app. En web su guía requiere configuración WASM y cabeceras COOP/COEP; por tanto, no debe asumirse que el mismo almacenamiento local nativo se despliega idéntico en navegador. [5] **VERIFICADO:** la guía de Flutter presenta repositorios como fuente única que combinan fuentes locales y remotas, con ejemplos de lectura cacheada y escritura offline-first; sincronización es una decisión de diseño. [6]

**VERIFICADO:** React Native facilita separar código por plataforma mediante `Platform` y extensiones `.ios`/`.android`; existe reutilización, pero no significa que todo código o interfaz sea idéntico. [7] Expo presenta SQLite como una base flexible que requiere combinar otras herramientas o construir sincronización para lograr una solución local-first completa; su guía califica el documento como trabajo en curso y advierte que el ecosistema sigue en fase temprana. [1] [5]

## Crítica de “RN Expo + PostgreSQL/Supabase + SQLite”

**VERIFICADO:** Supabase ofrece por proyecto PostgreSQL, APIs generadas, autenticación, Edge Functions, Realtime y Storage. [13] PostgreSQL es una base central; SQLite/Expo SQLite es una base del dispositivo. Son capas diferentes, no réplicas que se mantengan consistentes de forma implícita. Expo define local-first como lectura/escritura local con sincronización multi-dispositivo y advierte sobre permisos multiusuario, capa de sincronización personalizada y herramientas tempranas. [1] [5]

**VERIFICADO:** Row Level Security (RLS) de Supabase es autorización por fila en PostgreSQL, pero la documentación insiste en habilitar RLS en cada tabla expuesta, combinar políticas con grants mínimos, proteger vistas y probar tanto operaciones permitidas como denegadas. Una clave `service_role` evita RLS y debe permanecer en servidor. [14] Por ello, **INTERPRETACIÓN:** nunca almacenar secretos privilegiados en la app; definir tenant/organización y alcance de agricultor, técnico y administrador en servidor; probar controles también desde clientes no confiables. RLS no cifra por sí sola la base local ni diseña conflictos offline.

La propuesta es insuficiente si deja indeterminados: (1) identidad de registro y orden de cambios; (2) cola de salida durable; (3) ACK/reintentos/idempotencia; (4) política ante edición concurrente; (5) borrados y tombstones; (6) carga incremental/paginación; (7) adjuntos y reanudación; (8) expiración de credenciales; (9) esquema/versionado y migraciones locales; (10) auditoría y trazabilidad; (11) permisos administrativos e integración con sistemas externos. Estos son **requisitos de diseño propuestos (INTERPRETACIÓN)**, no capacidades atribuibles automáticamente a Supabase/Expo.

## Arquitectura recomendada

**INTERPRETACIÓN — propuesta base a validar:**

1. **Aplicaciones:** RN + Expo + TypeScript para Android/iOS. Portal administrativo React web separado si el uso de escritorio, tablas complejas, accesibilidad web o integración con sistemas existentes pesa más que reutilizar UI. Compartir monorepo de esquemas TypeScript, validación, reglas de dominio puras y cliente API; mantener adaptadores de plataforma y UI separados.
2. **Datos locales:** SQLite mediante Expo SQLite para datos operativos estructurados. Modelo por entidades con IDs UUID generados localmente, marcas `created_at/updated_at`, `server_version`, estado de sync, `deleted_at` y outbox. Migraciones numeradas y probadas. Cifrado local y ciclo de vida de claves deben definirse según clasificación de datos; no asumir que SQLite normal cifra. Expo documenta SQLCipher como opción nativa configurada al generar binarios, con salvedades de Expo Go y riesgo de configuración que no surta efecto si no se reconstruye. [5]
3. **Sincronización:** API de backend controlada (Edge Function o servicio propio) con operaciones idempotentes, cursor de cambios y lotes limitados. Una escritura local confirmada se muestra inmediatamente como “pendiente”; solo marcar “sincronizada” tras confirmación del servidor. Reintentos exponenciales con jitter y límites; registrar errores permanentes y ofrecer resolución/reintento visible. Diseñar resolución por campo/regla de negocio, no “última escritura gana” global por defecto. **PENDIENTE:** elección final de API, algoritmo de conflicto y política offline para cada entidad depende de reglas de Mágina Olivo.
4. **Servidor:** PostgreSQL como fuente autoritativa para datos compartidos y transacciones administrativas; RLS y grants mínimos en todas las tablas accesibles; migraciones versionadas; auditoría en servidor. Secretos privilegiados exclusivamente backend. Adjuntos a almacenamiento de objetos con carga reanudable y metadatos/ACL asociados, según capacidades probadas.
5. **Integración administrativa:** capa anticorrupción/API entre app y sistemas de Junta/administración. La integración concreta queda **PENDIENTE**: no se especifican organismo, endpoints, identidad federada, formatos, certificados, sandbox, base legal, ventanas de sincronización o SLA. No debe acoplarse el esquema móvil directamente a un formato administrativo no verificado.
6. **Operación:** observabilidad sin datos personales innecesarios; medición de cola pendiente, edad de último sync, errores/reintentos y tasa de conflictos; feature flags y despliegue escalonado. Definir responsable de actualización de dependencias y política de soporte iOS/Android.

## Requisitos de aceptación testables

Los umbrales siguientes son **INTERPRETACIÓN/propuesta de SLO para acordar**, no características de plataforma ni requisitos regulatorios. Deben aprobarse con usuarios y responsable de producto antes de convertirse en contrato.

- **Uso sin red:** en modo avión, iniciar la app y crear, editar, consultar y cerrar registros de campo definidos para el piloto; reiniciar el proceso y el dispositivo y verificar persistencia. Cero pérdida de cambios confirmados localmente en 100 ciclos de cierre forzado/prueba automatizada.
- **Recuperación/sync:** al restablecer conectividad, sincronizar 95% de 1.000 cambios pendientes de prueba en ≤5 minutos bajo red de referencia acordada, sin duplicados tras repetir petición/respuesta ni reintentos. Medir p50/p95 y declarar red, tamaño de lote y dispositivo.
- **Conflictos:** para cada entidad y campo editable, prueba de dos dispositivos que editan offline; resultado debe coincidir con regla documentada y mostrar conflicto cuando no haya resolución automática segura. Probar borrado concurrente, orden invertido, reloj desajustado y reintento idempotente.
- **Seguridad:** pruebas automáticas de RLS y grants para cada tabla/API: usuario A no lee/modifica datos de B ni cruza organizaciones; roles administrativos limitados por alcance; accesos anónimos denegados salvo contenido público explícito. Incluir intentos directos vía API, no solo pruebas de UI. Seguir procedimiento oficial de pruebas RLS. [14]
- **Migraciones:** cada versión soportada migra desde la versión anterior y desde al menos la versión más antigua soportada, preservando datos; fallo de migración no deja base parcialmente utilizable. Probar restauración desde backup donde proceda.
- **Rendimiento:** medir en dispositivos Android/iOS de gama mínima acordada; objetivo inicial sugerido p95 <300 ms para lectura local de listas de trabajo de 500 filas paginadas, y p95 <100 ms para respuesta de interacción inmediata. Perfilar con dataset realista, no atribuir estos objetivos a frameworks.
- **Escala backend:** prueba de carga con concurrencia, ráfagas de reconexión y volumen diario estimados para “miles de agricultores”; fijar números de usuarios activos, tamaño de registro, adjuntos y crecimiento antes del diseño final. Validar límites, latencia p95/p99, consultas, pool de conexiones, coste y plan de recuperación del proveedor. **PENDIENTE:** no se dispone de modelo de carga ni cotización vigente.
- **Calidad multiplataforma:** CI ejecuta análisis estático, unitarias de dominio, integración API/SQLite, pruebas de migración, UI y E2E en Android/iOS y navegador soportados; releases de prueba en dispositivos físicos para permisos, cámara/archivos, notificaciones, accesibilidad y mala conectividad. React Native advierte que los tests de componentes JS no validan código nativo iOS/Android. [10]
- **Builds y entrega:** builds reproducibles desde commit/tag, perfiles separados dev/QA/prod y custodia documentada de credenciales. EAS permite builds cloud/local, perfiles, distribución interna y CI, pero se debe decidir dependencia aceptable de servicio alojado y revisar límites/coste actuales. [9]
- **Web:** probar el portal en navegadores acordados con teclado/lector de pantalla, descargas e impresión, carga de tablas, roles administrativos y almacenamiento web. No asumir que `expo-sqlite` web es idéntico al móvil; la documentación exige WASM y encabezados de aislamiento. [5]

## Coste, mantenimiento y decisión

**VERIFICADO:** EAS Build es un servicio alojado con opción de build local; Supabase ofrece una plataforma administrada. [9] [13] **PENDIENTE:** sin alcance funcional, plantilla de personal, targets de soporte, uso de builds, región, límites de datos/tráfico, SLA y precios contractuales consultados en el momento de compra, no existe base para afirmar un ganador de coste monetario. Las cuotas pueden cambiar; cotizar y modelar escenarios antes de comprometerse.

**INTERPRETACIÓN:** para limitar costes de cambio, evitar microservicios prematuros y aislar el dominio del proveedor: API/contratos versionados, migraciones SQL en control de versiones, repositorios de datos, modelo local explícito y exportabilidad/backup. Adoptar un backend administrado reduce trabajo de operar infraestructura, pero aumenta dependencia del proveedor y no sustituye diseño de seguridad, migración, continuidad ni pruebas de capacidad. La arquitectura recomendada sigue condicionada a un piloto que mida trabajo offline real, usabilidad y coste de soporte.

### Decisiones pendientes que pueden cambiar la recomendación

- ¿“Web” significa portal interno de gestión con tablas/impresión/roles o app de campo idéntica en navegador?
- ¿Qué trámites/sistemas administrativos se integran y mediante qué interfaces autorizadas?
- ¿Qué datos se capturan, cuánto tiempo deben permanecer offline y cuáles requieren validez/transmisión inmediata?
- ¿Qué se considera resolución válida de conflicto en cada entidad y quién puede sobrescribir?
- ¿Qué dispositivos mínimos, versiones de SO, idiomas, accesibilidad y conectividad rural son objetivo?
- ¿Volumen de usuarios concurrentes, registros/día, tamaño de adjuntos, retención, región y SLA?
- ¿Requisitos de protección de datos, clasificación, conservación y cifrado definidos por responsable jurídico/seguridad? No se infieren aquí obligaciones legales concretas.
- ¿Presupuesto total de tres años, composición/experiencia del equipo, costes de tiendas, proveedores, soporte y operación?
