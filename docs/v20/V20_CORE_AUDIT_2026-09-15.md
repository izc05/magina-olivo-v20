## Resumen ejecutivo

No hay que rehacer V20 desde cero. El candidate ya contiene una base funcional importante de los tres pilares. La prioridad debe ser **consolidar lo existente sobre un vertical real de Bedmar**, absorber solo deltas útiles de ramas especializadas y evitar merges directos de ramas antiguas muy divergidas.

La secuencia recomendada es:

`Aventura senderismo end-to-end → Mi Olivo premium conectado → Recompensa AOVE/QR → Mi Campo núcleo → Inicio alrededor de los tres pilares`

### Limitaciones actuales verificadas

- La grabación GPS actual es **foreground web**: necesita la web abierta; el propio componente avisa de que el navegador puede suspender GPS con pantalla apagada.

- El modo offline completo no está cerrado.
- Falta una prueba física de campo real en Bedmar.

## 5. Decisiones de integración

1. `integrate/v20-beta-closure` sigue siendo la base técnica de referencia para implementar el siguiente vertical.
2. No usar `main` para desarrollo.
3. No mergear ramas especializadas antiguas muy divergidas.
4. Crear ramas frescas desde candidate para cada vertical.
5. Portar deltas con comparación de archivos y tests, no por nombre de rama.
6. La primera rama nueva debe cerrar **Bedmar Aventura vertical**.
7. Después: **Mi Olivo Premium conectado a esa aventura**.
8. Después: **AOVE/QR piloto** sobre flujo ya existente.
9. Después: **Mi Campo núcleo y pulido**.
10. Solo entonces rediseñar Inicio y ampliar contenido secundario.

## 6. Primera definición de terminado — Bedmar vertical

Un vertical de Bedmar se considera cerrado cuando un usuario puede:

1. iniciar sesión;
2. ver una ruta real de Bedmar con track validado;
3. revisar dificultad, desnivel, seguridad y condiciones;
4. iniciar grabación y Modo Aventura;
5. ver su posición GPS en el mapa;
6. seguir el track;
7. desbloquear checkpoints reales por proximidad;
8. completar al menos un reto;
9. finalizar la ruta;
10. recibir XP/aceitunas/colección;
11. ver el progreso reflejado en Mi Olivo;
12. reservar una recompensa AOVE si tiene saldo;
13. generar QR;
14. validar el QR una sola vez;
15. conservar el historial;
16. superar CI y pruebas físicas en móvil.

## 7. Riesgos que no debemos ocultar

- Una PWA web no garantiza GPS continuo con pantalla apagada en todos los móviles. V20 web debe comunicar esta limitación y diseñar una recuperación robusta; una app nativa/Capacitor puede ser la evolución posterior.
- Offline completo para mapas requiere estrategia concreta de tiles/cache y debe validarse legal/técnicamente con el proveedor cartográfico usado.
- XP/aceitunas deben concederse en servidor y ser idempotentes para evitar duplicados por reintentos.
- QR/stock debe resolverse transaccionalmente para impedir doble reserva o doble canje.
- Checkpoints deben validarse físicamente sobre el terreno antes de publicación.
